# DevOps

## Lab: Kubernetes Rolling Update

### Objective

Deploy the latest application changes by performing a **rolling update** on the existing deployment without downtime.

---

## Existing Resource

Deployment

```text
nginx-deployment
```

Current Image

```text
nginx:1.19
```

Target Image

```text
nginx:1.18
```

---

## Step 1 – Verify Deployment

Checked the deployment before making any changes.

```bash
kubectl get deployment nginx-deployment
```

Verified the container image.

```bash
kubectl describe deployment nginx-deployment
```

or

```bash
kubectl get deployment nginx-deployment -o=jsonpath='{.spec.template.spec.containers[*].image}'
```

---

## Step 2 – Perform Rolling Update

Updated the deployment image without deleting or recreating the deployment.

```bash
kubectl set image deployment/nginx-deployment nginx=nginx:1.18
```

If the container name was unknown, it could be identified using:

```bash
kubectl get deployment nginx-deployment -o=jsonpath='{.spec.template.spec.containers[*].name}'
```

---

## Step 3 – Monitor Rollout

Tracked the rolling update.

```bash
kubectl rollout status deployment/nginx-deployment
```

Expected

```text
deployment "nginx-deployment" successfully rolled out
```

---

## Step 4 – Verify Pods

```bash
kubectl get pods
```

Confirmed every pod reached the **Running** state.

Verified the updated image.

```bash
kubectl describe deployment nginx-deployment
```

---

## Learning

* Rolling updates replace pods gradually without application downtime.
* `kubectl rollout status` provides the rollout progress.
* Existing deployment resources remain intact while updating the application version.

# MLOps

## Lab: Convert Single-Stage Docker Build into Multi-Stage Build

### Objective

Optimize the fraud-detection serving image by separating the training environment from the runtime environment.

---

## Existing Project

```text
/root/code/ml-serve/
│
├── train_model.py
├── serve.py
└── Dockerfile
```

---

## Builder Stage

Used the Python base image.

```dockerfile
FROM python:3.11-slim AS builder
```

Configured working directory.

```dockerfile
WORKDIR /app
```

Installed only training dependencies.

```dockerfile
RUN pip install --no-cache-dir \
    scikit-learn \
    pandas \
    numpy \
    joblib
```

Copied training script.

```dockerfile
COPY train_model.py .
```

Generated the trained model.

```dockerfile
RUN python3 train_model.py
```

Produced

```text
/app/model.pkl
```

---

## Runtime Stage

Started a fresh lightweight image.

```dockerfile
FROM python:3.11-slim
```

Configured working directory.

```dockerfile
WORKDIR /app
```

Installed only runtime dependencies.

```dockerfile
RUN pip install --no-cache-dir \
    flask \
    joblib \
    numpy \
    scikit-learn
```

Copied the serving application.

```dockerfile
COPY serve.py .
```

Copied the trained model from the builder stage.

```dockerfile
COPY --from=builder /app/model.pkl .
```

Started the Flask application.

```dockerfile
CMD ["python3","serve.py"]
```

---

## Build

```bash
cd /root/code/ml-serve

docker build -t ml-serve:v1 .
```

---

## Verification

Verified image.

```bash
docker images ml-serve:v1
```

Started container.

```bash
docker run --rm -p 8090:8080 ml-serve:v1
```

Health endpoint.

```bash
curl http://localhost:8090/health
```

Expected

```json
{"status":"ok"}
```

---

## Issue Encountered

Container startup failed.

```text
Bind for 0.0.0.0:8090 failed:
port is already allocated
```

Investigation

```bash
ss -tulpn | grep 8090
```

Discovered

```text
docker-proxy
```

Further inspection

```bash
docker ps
```

Found an existing container:

```text
trusting_tu
```

using

```text
0.0.0.0:8090 -> 8080
```

Resolution

Stopped and removed the running container.

```bash
docker stop trusting_tu

docker rm trusting_tu
```

---

## Learning

* Multi-stage Docker builds significantly reduce runtime image size.
* Runtime images should contain only the serving application, model, and required runtime libraries.
* Port conflicts caused by previously running containers must be resolved before validation.

# Linux

## Lab: Install Squid on All Application Servers

### Objective

Install Squid on every application server and ensure it starts automatically after reboot.

---

## Target Servers

```text
App Server 1
App Server 2
App Server 3
```

---

## Installation

Connected to each application server.

Installed Squid.

```bash
sudo yum install -y squid
```

Enabled automatic startup.

```bash
sudo systemctl enable squid
```

---

## Verification

Verified installation.

```bash
rpm -q squid
```

Verified boot configuration.

```bash
systemctl is-enabled squid
```

Expected

```text
enabled
```

---

## Learning

* `yum install` installs the required package.
* `systemctl enable` configures the service to start automatically during system boot.
* Enabling a service is different from starting it immediately.

# Kubernetes

## Lab: Expose ReplicaSet Using NodePort Service

### Objective

Expose an existing ReplicaSet through a Kubernetes NodePort Service without modifying the ReplicaSet.

---

## Existing Resource

ReplicaSet

```text
httpd-replicaset
```

Pod Labels

```text
app=httpd_app

type=front-end
```

---

## Service Requirements

Service Name

```text
httpd-service
```

Service Type

```text
NodePort
```

Application Port

```text
80
```

NodePort

```text
30080
```

---

## YAML

```yaml
apiVersion: v1
kind: Service
metadata:
  name: httpd-service

spec:
  type: NodePort

  selector:
    app: httpd_app
    type: front-end

  ports:
  - port: 80
    targetPort: 80
    nodePort: 30080
```

---

## Deployment

Applied the manifest.

```bash
kubectl apply -f httpd-service.yaml
```

---

## Verification

Checked the Service.

```bash
kubectl get svc httpd-service
```

Verified endpoints.

```bash
kubectl get endpoints httpd-service
```

Confirmed that the Service routed traffic to the ReplicaSet pods.

---

## Learning

* A Service exposes pods using labels rather than pod names.
* ReplicaSets remain unchanged when a Service is created.
* NodePort makes an application reachable on every Kubernetes node through a fixed port.
