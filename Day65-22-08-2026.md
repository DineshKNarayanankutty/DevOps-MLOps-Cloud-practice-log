# DevOps (Kubernetes)

## Task: Deploy Redis with ConfigMap and Volumes

### Objective

Deploy Redis on a Kubernetes cluster for testing, using a ConfigMap for Redis configuration and an `emptyDir` volume for Redis data.

### Requirements

```text
ConfigMap: my-redis-config
ConfigMap key: redis-config
Configuration: maxmemory 2mb

Deployment: redis-deployment
Replica: 1
Image: redis:alpine
Container: redis-container
Container Port: 6379
CPU Request: 1

Data volume:
  Type: emptyDir
  Mount: /redis-master-data

Config volume:
  Type: ConfigMap
  Mount: /redis-master
```

### `redis.yaml`

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-redis-config
data:
  redis-config: |
    maxmemory 2mb
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis-container
          image: redis:alpine
          ports:
            - containerPort: 6379
          resources:
            requests:
              cpu: "1"
          volumeMounts:
            - name: data
              mountPath: /redis-master-data
            - name: redis-config
              mountPath: /redis-master
      volumes:
        - name: data
          emptyDir: {}
        - name: redis-config
          configMap:
            name: my-redis-config
```

### Commands Used

Apply the configuration:

```bash
kubectl apply -f redis.yaml
```

Verify the ConfigMap:

```bash
kubectl get configmap my-redis-config
```

```bash
kubectl describe configmap my-redis-config
```

Verify the Deployment:

```bash
kubectl get deployment redis-deployment
```

Verify the Pod:

```bash
kubectl get pods
```

Verify complete resources:

```bash
kubectl get all
```

### Key Learning

* ConfigMaps can be used to provide application configuration to containers.
* `emptyDir` provides temporary pod-local storage.
* ConfigMap volumes allow configuration to be mounted as files.
* Kubernetes resource requests define the minimum amount of CPU requested by a container.
* A Deployment manages the desired number of pod replicas.
* Redis uses port `6379` by default.

# Terraform

## Task: Create SNS Topic and SQS Queue with Subscription

### Objective

Provision an AWS SNS topic and SQS queue using Terraform and subscribe the SQS queue to the SNS topic so that messages published to SNS can be delivered to SQS.

### Requirements

```text
SNS Topic: devops-sns-topic

SQS Queue: devops-sqs-queue

Subscription:
SNS → SQS

SNS Topic ARN output:
kke_sns_topic_arn

SQS Queue URL output:
kke_sqs_queue_url
```

### Files Used

```text
main.tf
outputs.tf
```

### `main.tf`

```hcl
resource "aws_sns_topic" "devops_sns_topic" {
  name = "devops-sns-topic"
}

resource "aws_sqs_queue" "devops_sqs_queue" {
  name = "devops-sqs-queue"
}

resource "aws_sns_topic_subscription" "sqs_subscription" {
  topic_arn = aws_sns_topic.devops_sns_topic.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.devops_sqs_queue.arn
}

resource "aws_sqs_queue_policy" "devops_sqs_queue_policy" {
  queue_url = aws_sqs_queue.devops_sqs_queue.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          Service = "sns.amazonaws.com"
        }
        Action   = "sqs:SendMessage"
        Resource = aws_sqs_queue.devops_sqs_queue.arn
        Condition = {
          ArnEquals = {
            "aws:SourceArn" = aws_sns_topic.devops_sns_topic.arn
          }
        }
      }
    ]
  })
}
```

### `outputs.tf`

```hcl
output "kke_sns_topic_arn" {
  value = aws_sns_topic.devops_sns_topic.arn
}

output "kke_sqs_queue_url" {
  value = aws_sqs_queue.devops_sqs_queue.url
}
```

### Commands Used

Check outputs:


AWS verification:

```bash

```

### Key Learning

* SNS provides publish/subscribe messaging.
* SQS provides durable message queuing.
* SNS can deliver messages to an SQS queue through a subscription.
* The SQS queue policy must allow the SNS service to send messages.
* Terraform resource references allow the SNS topic and SQS queue to be connected dynamically.
* Terraform outputs expose important resource information such as ARNs and URLs.

# Linux

## Task: GPG File Encryption and Decryption

### Objective

Use GPG public and private keys on the storage server to encrypt confidential data before transfer and decrypt received data.

### Environment

```text
Server: storage server
Key location: /home/*_key.asc
User ID: kodekloud@kodekloud.com
Passphrase: kodekloud

Input for encryption:
 /home/encrypt_me.txt

Encrypted output:
 /home/encrypted_me.asc

Encrypted input:
 /home/decrypt_me.asc

Decrypted output:
 /home/decrypted_me.txt
```

### Step 1 — Check the Keys

```bash
ls -l /home/*_key.asc
```

Import the keys:

```bash
gpg --import /home/*_key.asc
```

Verify the imported keys:

```bash
gpg --list-keys
```

### Step 2 — Encrypt the File

```bash
gpg --armor --output /home/encrypted_me.asc \
    --encrypt \
    --recipient kodekloud@kodekloud.com \
    /home/encrypt_me.txt
```

### Step 3 — Decrypt the File

```bash
gpg --output /home/decrypted_me.txt \
    --decrypt /home/decrypt_me.asc
```

Use the provided passphrase when prompted:

```text
kodekloud
```

### Step 4 — Verify the Files

```bash
ls -l /home/encrypt_me.txt /home/encrypted_me.asc
```

```bash
ls -l /home/decrypt_me.asc /home/decrypted_me.txt
```

Verify decrypted content:

```bash
cat /home/decrypted_me.txt
```

### Key Learning

* GPG supports public-key encryption and private-key decryption.
* The recipient's public key is used to encrypt data.
* The corresponding private key is required to decrypt the data.
* `gpg --import` imports existing public/private keys.
* `gpg --list-keys` verifies imported public keys.
* `--armor` creates ASCII-armored output, commonly used for `.asc` files.
* Encryption protects confidential data during transfer to remote locations.

# MLOps

## Task: Implement Canary Deployment Policy

### Objective

Implement a pure-Python canary deployment policy that gradually shifts traffic from model v1 to model v2 and rolls back if the v2 error rate exceeds the configured threshold.

### Project Directory

```text
/root/code/serving/
```

### Deployment Strategy

```text
Phase 1 → 95% v1 / 5% v2
Phase 2 → 70% v1 / 30% v2
Phase 3 → 0% v1 / 100% v2
```

### Canary Configuration

The simulated v2 error rate is:

```text
2%
```

Rollback threshold:

```text
5%
```

Therefore:

```python
ROLLBACK_THRESHOLD = 0.05
```

A healthy v2 with a simulated `2%` error rate remains below the `5%` rollback threshold.

### `promote()` Logic

```python
def promote(self) -> tuple[float, float]:
    """Advance to the next phase's traffic weights."""
    self.phase += 1

    if self.phase == 1:
        self.v1_weight = 0.95
        self.v2_weight = 0.05
    elif self.phase == 2:
        self.v1_weight = 0.70
        self.v2_weight = 0.30
    elif self.phase == 3:
        self.v1_weight = 0.00
        self.v2_weight = 1.00

    return self.v1_weight, self.v2_weight
```

### Commands Used

Navigate to the project:

```bash
cd /root/code/serving
```

Run the simulator:

```bash
python3 canary_deploy.py
```

### Expected Rollout

```text
Phase 1: v1=95% v2=5%
Phase 2: v1=70% v2=30%
Phase 3: v1=0% v2=100%

Total requests: 300
OUTCOME: PROMOTED
```

### Key Learning

* Canary deployments gradually expose a new application/model version to production traffic.
* Traffic can be increased progressively after each successful health check.
* Error-rate thresholds can be used as automated rollback criteria.
* A healthy candidate should remain below the rollback threshold.
* The rollout strategy used was `95/5 → 70/30 → 0/100`.
* The simulator helps validate deployment logic before implementing the same strategy with tools such as Argo Rollouts.
* Canary deployments reduce the risk of immediately sending 100% of production traffic to a new version.
