## 1. DevOps – Jenkins: Configure Job-Level Permissions

### Objective

The xFusionCorp Industries development team required two existing Jenkins users to access an existing job named `Packages`, with different permissions.

### Environment

- Application: Jenkins
- Login: Jenkins UI through the KodeKloud top navigation bar
- Administrator username: `admin`
- Existing job: `Packages`
- Existing users: `sam`, `rohan`

### Requirements

| User | Required permissions |
|---|---|
| sam | Build, Configure, Read |
| rohan | Build, Cancel, Configure, Read, Update, Tag |

Additional requirement:
- Select `Inherit permissions from parent ACL`.
- Do not modify any other job configuration.

### Steps to perform

**Step 1: Login to Jenkins**

1. Click the Jenkins button on the KodeKloud top bar.
2. Login using the administrator credentials supplied by the lab.

**Step 2: Install the authorization plugin if required**

Navigate to:

`Manage Jenkins → Plugins`

Search for:

`Matrix Authorization Strategy`

Install the plugin if it is not already installed.

If Jenkins requires a restart:
- Wait until no jobs are running.
- Restart Jenkins.
- Refresh the UI after restarting.

**Step 3: Open the Packages job**

1. Navigate to the Jenkins dashboard.
2. Open `Packages`.
3. Click `Configure`.
4. Enable `Enable project-based security`.

**Step 4: Configure inheritance strategy**

Under the project-based security section, select:

`Inherit permissions from parent ACL`

**Step 5: Configure sam permissions**

Add user `sam` and select:

- Job → Build
- Job → Configure
- Job → Read

Do not select additional permissions.

**Step 6: Configure rohan permissions**

Add user `rohan` and select:

- Job → Build
- Job → Cancel
- Job → Configure
- Job → Read
- Job → Update
- Job → Tag

**Step 7: Save**

Click Save and verify that both users appear in the Packages permission matrix.

### Final expected configuration

| Permission | sam | rohan |
|---|:---:|:---:|
| Build | Yes | Yes |
| Cancel | No | Yes |
| Configure | Yes | Yes |
| Read | Yes | Yes |
| Update | No | Yes |
| Tag | No | Yes |

### Important learning points

- Matrix Authorization Strategy allows permissions to be assigned individually.
- Project-based security allows job-specific permissions.
- Inheritance from parent ACL retains permissions inherited from the parent security configuration.
- Global Jenkins security and individual job security are different.
- Always modify only the requested job when handling job-level access requirements.

### Verification

Confirm:
- Project-based security is enabled.
- Inheritance strategy is correct.
- sam has exactly the requested permissions.
- rohan has exactly the requested permissions.
- No other job configurations were modified.

## 3. Kubernetes – Deploy Tomcat Application Using NodePort

### Objective

Deploy a Java-based Tomcat application into an existing Kubernetes cluster.

The application must run in a dedicated namespace and be exposed through a NodePort service.

### Requirements

| Resource | Configuration |
|---|---|
| Namespace | tomcat-namespace-xfusion |
| Deployment | tomcat-deployment-xfusion |
| Replicas | 1 |
| Container | tomcat-container-xfusion |
| Image | kodekloud/centos-ssh-enabled:tomcat |
| Container port | 8080 |
| Service | tomcat-service-xfusion |
| Service type | NodePort |
| NodePort | 32227 |

### Environment

- Machine: KodeKloud jump-host.
- Kubernetes CLI: `kubectl`.
- Cluster context: Already configured.

### Step 1: Create the namespace

```bash
kubectl create namespace tomcat-namespace-xfusion
```

Verify:

```bash
kubectl get namespaces
```

### Step 2: Create the deployment

A declarative YAML manifest is used to ensure the exact deployment and container names.

Create the file:

```bash
cat <<'EOF' > tomcat-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tomcat-deployment-xfusion
  namespace: tomcat-namespace-xfusion
spec:
  replicas: 1
  selector:
    matchLabels:
      app: tomcat-xfusion
  template:
    metadata:
      labels:
        app: tomcat-xfusion
    spec:
      containers:
        - name: tomcat-container-xfusion
          image: kodekloud/centos-ssh-enabled:tomcat
          ports:
            - containerPort: 8080
EOF
```

Apply:

```bash
kubectl apply -f tomcat-deployment.yaml
```

### Alternative imperative creation

The deployment can initially be created using:

```bash
kubectl create deployment tomcat-deployment-xfusion \
  --image=kodekloud/centos-ssh-enabled:tomcat \
  --replicas=1 \
  --namespace=tomcat-namespace-xfusion
```

However, this initially generates a container name automatically. Use the declarative manifest above to guarantee the required container name.

### Step 3: Create the NodePort service

Create:

```bash
cat <<'EOF' > tomcat-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: tomcat-service-xfusion
  namespace: tomcat-namespace-xfusion
spec:
  type: NodePort
  selector:
    app: tomcat-xfusion
  ports:
    - port: 8080
      targetPort: 8080
      nodePort: 32227
      protocol: TCP
EOF
```

Apply:

```bash
kubectl apply -f tomcat-service.yaml
```

### Step 4: Verify deployment rollout

```bash
kubectl rollout status deployment/tomcat-deployment-xfusion \
  -n tomcat-namespace-xfusion
```

### Step 5: Verify pods

```bash
kubectl get pods -n tomcat-namespace-xfusion -o wide
```

Expected:

```text
NAME                                      READY   STATUS
tomcat-deployment-xfusion-xxxxx           1/1     Running
```

### Step 6: Verify deployment

```bash
kubectl get deployment tomcat-deployment-xfusion \
  -n tomcat-namespace-xfusion
```

Expected:

```text
READY   UP-TO-DATE   AVAILABLE
1/1     1            1
```

### Step 7: Verify service

```bash
kubectl get svc tomcat-service-xfusion \
  -n tomcat-namespace-xfusion
```

Expected:

```text
NAME                   TYPE       PORT(S)
tomcat-service-xfusion NodePort   8080:32227/TCP
```

### Step 8: Verify endpoints

```bash
kubectl get endpoints tomcat-service-xfusion \
  -n tomcat-namespace-xfusion
```

Expected:
- A Pod IP should appear.
- Port should be 8080.
- Endpoints should not be `<none>`.

### Step 9: Test application connectivity

Get node IP:

```bash
kubectl get nodes -o wide
```

Test NodePort:

```bash
curl -I http://<NODE-IP>:32227
```

If the node IP is inaccessible from the jump-host, test the service internally:

```bash
kubectl run tomcat-test \
  --rm -it \
  --restart=Never \
  --image=curlimages/curl \
  -n tomcat-namespace-xfusion \
  -- curl -I http://tomcat-service-xfusion:8080
```

### Step 10: Final verification

```bash
kubectl get all -n tomcat-namespace-xfusion
```

Expected resources:

```text
deployment.apps/tomcat-deployment-xfusion
pod/tomcat-deployment-xfusion-xxxxx
service/tomcat-service-xfusion
```

### Important Kubernetes learning points

- Namespace provides logical isolation for Kubernetes resources.
- Deployment manages ReplicaSets and application pods.
- Replica count controls the desired number of pod instances.
- Labels and selectors connect services to pods.
- Container port specifies the application port inside the container.
- NodePort exposes a service on a port across cluster nodes.
- `targetPort` identifies the container-facing port.
- `port` is the service-facing port.
- `nodePort` is the externally exposed node port.
- `kubectl rollout status` checks whether a deployment has completed successfully.
- Service endpoints help identify whether the service selector matches ready pods.
