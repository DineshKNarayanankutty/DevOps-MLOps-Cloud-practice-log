# DevOps

## MariaDB Service Troubleshooting on Database Server

### Task

Investigated and resolved a production issue where the application could not connect to the database because the MariaDB service was down.

---

### Check Service Status

```bash
systemctl status mariadb.service
```

Observed error:

```text
Cannot change ownership of the database directories
chown: changing ownership of '/var/lib/mysql': Operation not permitted
Initialization of MariaDB database failed
```

---

### Verify MySQL Directory Ownership

```bash
ls -ld /var/lib/mysql
```

---

### Check File Attributes

```bash
lsattr -d /var/lib/mysql
```

or

```bash
lsattr -R /var/lib/mysql
```

---

### Remove Immutable Attribute (if present)

```bash
chattr -i /var/lib/mysql
```

Recursive option if required:

```bash
chattr -R -i /var/lib/mysql
```

---

### Correct Ownership

```bash
chown -R mysql:mysql /var/lib/mysql
```

---

### Start MariaDB Service

```bash
systemctl start mariadb
```

---

### Verify Service Status

```bash
systemctl status mariadb
```

Expected:

```text
active (running)
```

---

### Simple Explanation

MariaDB failed because it could not modify files under `/var/lib/mysql`.

The issue was related to incorrect ownership or immutable file attributes preventing MariaDB from accessing its data directory.

---

### Why This Is Important

Database outages directly impact application availability.

This task reinforces:

* Linux troubleshooting
* Service recovery
* Database administration
* Permission management
* Production incident handling

# MLOps

## Cookiecutter ML Project Template Creation

### Task

Fixed an ML project Cookiecutter template and generated a new project from it.

---

### Navigate to Template Directory

```bash
cd /root/code/mlops-template
```

---

### Fix cookiecutter.json

```json
{
    "project_name": "my-ml-project",
    "author": "xFusionCorp",
    "python_version": "3.11",
    "ml_framework": ["sklearn", "pytorch", "tensorflow"]
}
```

---

### Create Required Template Structure

```bash
mkdir -p "{{cookiecutter.project_name}}"/{data,models,src,tests}
```

---

### README Template

```markdown
# {{ cookiecutter.project_name }}

Author: {{ cookiecutter.author }}

Python Version: {{ cookiecutter.python_version }}
```

---

### requirements.txt Template

```jinja
{% if cookiecutter.ml_framework == "sklearn" %}
scikit-learn
{% elif cookiecutter.ml_framework == "pytorch" %}
torch
{% elif cookiecutter.ml_framework == "tensorflow" %}
tensorflow
{% endif %}
```

---

### Generate Project

```bash
cookiecutter /root/code/mlops-template/ \
-o /root/code/ \
--no-input \
project_name=churn-model \
ml_framework=sklearn
```

---

### Verify Generated Project

```bash
tree /root/code/churn-model
```

---

### Verify Dependencies

```bash
cat /root/code/churn-model/requirements.txt
```

Expected:

```text
scikit-learn
```

---

### Verify README

```bash
cat /root/code/churn-model/README.md
```

Expected to contain:

```text
churn-model
xFusionCorp
```

---

### Simple Explanation

Cookiecutter allows teams to generate standardized project structures automatically.

Instead of manually creating directories and files, developers can generate complete projects from a template.

---

### Why This Is Important

Benefits:

* Faster project creation
* Standardized repository layouts
* Consistent engineering practices
* Better onboarding for teams
* Reproducible ML project structures

# Terraform

## Create AWS EBS Volume

### Task

Provisioned an AWS EBS volume using Terraform.

---

### Navigate to Terraform Directory

```bash
cd /home/bob/terraform
```

---

### Edit main.tf

```bash
vi main.tf
```

---

### Terraform Configuration

```hcl
resource "aws_ebs_volume" "datacenter_volume" {
  availability_zone = "us-east-1a"
  size              = 2
  type              = "gp3"

  tags = {
    Name = "datacenter-volume"
  }
}
```

---

### Initialize Terraform

```bash
terraform init
```

---

### Apply Configuration

```bash
terraform apply -auto-approve
```

---

### Verify Resources

```bash
terraform state list
```

Expected:

```text
aws_ebs_volume.datacenter_volume
```

---

### Simple Explanation

Created a persistent AWS block storage volume.

The volume:

* Uses gp3 storage
* Has 2 GiB capacity
* Is tagged as `datacenter-volume`

---

### Why This Is Important

EBS volumes are used for:

* EC2 instance storage
* Databases
* Application data
* Persistent workloads

Using Terraform ensures storage provisioning is automated and repeatable.
