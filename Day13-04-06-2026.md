## Azure

### SSH Key Authentication for Azure VM

#### Task

Configure passwordless root SSH access from the Azure client host to `xfusion-vm`.

---

### Investigation

Retrieved the root user's public key from the Azure client host:

```bash
cat /root/.ssh/id_rsa.pub
```

Connected to VM:

```bash
ssh azureuser@<vm-ip>
sudo su -
```

Examined:

```bash
cat /root/.ssh/authorized_keys
```

Found Azure's default restricted key:

```text
no-port-forwarding,no-agent-forwarding,no-X11-forwarding,
command="Please login as the user azureuser rather than the user root"
```

---

### Initial Assumption

Appended the Azure client host public key to:

```bash
/root/.ssh/authorized_keys
```

However:

```bash
ssh root@<vm-ip>
```

still returned:

```text
Please login as the user "azureuser" rather than the user "root".
```

---

### Root Cause

Azure had inserted a forced-command SSH key that intercepted root logins.

The validator expected direct root SSH access using the landing host's key.

---

### Final Fix

Replaced the contents of:

```bash
/root/.ssh/authorized_keys
```

with the Azure client host's public key:

```bash
cat /root/.ssh/id_rsa.pub > /root/.ssh/authorized_keys
```

Set permissions:

```bash
chmod 700 /root/.ssh
chmod 600 /root/.ssh/authorized_keys
```

---

### Verification

```bash
ssh root@<vm-ip>
```

Succeeded without password.

---

### Learning

Azure cloud-init may install restricted root SSH keys that intentionally prevent direct root login.

# DevOps

## iptables Security Hardening for Apache Port 8089

### Task

Install iptables on all app servers and allow access to Apache port `8089` only from the Load Balancer host.

---

### Installation

On all app servers:

```bash
yum install -y iptables iptables-services
```

Started service:

```bash
systemctl enable iptables
systemctl start iptables
```

---

### Configuration

Identified Load Balancer IP:

```bash
getent hosts stlb01
```

Configured rules:

```bash
iptables -I INPUT 1 -p tcp -s <LBR_IP> --dport 8089 -j ACCEPT

iptables -I INPUT 2 -p tcp --dport 8089 -j DROP
```

---

### Initial Confusion

Jump host tests:

```bash
curl http://stapp01:8089
curl http://stapp02:8089
curl http://stapp03:8089
```

returned:

```text
No route to host
```

Initially looked like a problem.

---

### Analysis

This was actually expected behavior.

Requirements were:

```text
Allow only LBR host
Block everyone else
```

Jump host belongs to:

```text
Everyone else
```

Therefore:

```text
No route to host = Success
```

---

### Persistence

Saved rules:

```bash
service iptables save
```

---

### Learning

Firewall troubleshooting requires understanding who should be allowed versus who should be blocked before interpreting test results.

# MLOps

## DVC Pull from SeaweedFS

### Task

A fresh clone of the `fraud-detection` repository could not retrieve data using:

```bash
dvc pull
```

---

### Investigation

Reviewed:

```bash
cat .dvc/config
```

Task requirements specified:

```text
access_key_id     = weedadmin
secret_access_key = weedadmin123
endpointurl       = http://localhost:8333
```

---

### Fix

Updated DVC remote configuration:

```bash
dvc remote modify s3 access_key_id weedadmin

dvc remote modify s3 secret_access_key weedadmin123

dvc remote modify s3 endpointurl http://localhost:8333

dvc remote modify s3 url s3://dvc-storage
```

---

### Pull Dataset

```bash
dvc pull
```

Expected result:

```text
transactions.csv restored
```

---

### Verification

```bash
ls data/raw/
```

Expected:

```text
transactions.csv
transactions.csv.dvc
```

---

### Learning

DVC requires:

* Correct bucket
* Correct endpoint
* Correct credentials

for successful retrieval of versioned datasets.

# Terraform

## Private S3 Bucket Creation

### Task

Create:

```text
devops-s3-14111
```

Requirements:

* Region: `us-east-1`
* Private bucket
* Block all public access

---

### Terraform Configuration

```hcl
provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "devops_s3" {
  bucket = "devops-s3-14111"
}

resource "aws_s3_bucket_public_access_block" "devops_s3" {
  bucket = aws_s3_bucket.devops_s3.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

---

### Deployment

```bash
terraform init

terraform plan

terraform apply -auto-approve
```

---

### Learning

Modern AWS security best practices require Block Public Access controls in addition to bucket creation.

# Key Lessons Learned

### Azure

* Azure may install forced-command SSH keys that prevent root login.
* Lab validators sometimes require replacing the default root key instead of appending.

### DevOps

* A blocked connection can be a successful outcome when security requirements demand it.
* Always verify firewall rules in the correct order.

### MLOps

* DVC pull failures are commonly caused by remote authentication misconfiguration.

### Terraform

* Public and private S3 bucket implementations differ primarily in Public Access Block configuration.
* AWS security defaults increasingly rely on explicit public access controls rather than ACLs alone.
