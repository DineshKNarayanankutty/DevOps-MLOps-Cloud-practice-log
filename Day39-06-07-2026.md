# MLOps

# Device-Aware PyTorch Training with MLflow

## Objective

Modify a PyTorch training script to automatically detect CPU or GPU availability, eliminate hardcoded CUDA usage, and accurately log the training device in MLflow.

---

## Problems Identified

The original trainer assumed CUDA was always available:

```python
model = model.cuda()

xb = X_t.cuda()

yb = y_t.cuda()
```

It also logged:

```python
mlflow.log_param("device", "cuda")
```

which was incorrect on CPU-only systems.

---

## Code Changes

Created a device object:

```python
device = torch.device(
    "cuda" if torch.cuda.is_available() else "cpu"
)
```

Updated model:

```python
model = FraudNet().to(device)
```

Updated tensors:

```python
xb = X_t.to(device)
yb = y_t.to(device)
```

Updated MLflow logging:

```python
mlflow.log_param("device", str(device))
```

---

## Execute Training

```bash
cd /root/code/fraud-detection

python3 src/models/train_pytorch.py
```

# Terraform

# Creating an AWS IAM Role Using Variables

## Objective

Provision an IAM Role using Terraform while storing the role name in a reusable variable.

---

## Directory

```text
/home/bob/terraform
```

---

## variables.tf

```hcl
variable "KKE_iamrole" {
  description = "IAM Role Name"
  type        = string
  default     = "iamrole_james"
}
```

---

## main.tf

```hcl
provider "aws" {
  region = "us-east-1"
}

resource "aws_iam_role" "role" {
  name = var.KKE_iamrole

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = {
        Service = "ec2.amazonaws.com"
      }
      Action = "sts:AssumeRole"
    }]
  })

  tags = {
    Name = var.KKE_iamrole
  }
}
```

---

## Commands Executed

```bash
cd /home/bob/terraform

terraform init

terraform validate

terraform plan

terraform apply -auto-approve

terraform state list
```

---

## Architecture

```text

      │
      ▼

      │
      ▼
main.tf
      │

      │
Terraform Apply
      ▼

```

---

## Key Learning

Unlike IAM Users, IAM Roles require an **Assume Role (Trust) Policy** that defines which AWS service or principal is allowed to use the role.

# Issues Encountered Today

### PyTorch Device Compatibility

The training script failed on CPU-only systems because it used hardcoded `.cuda()` calls. Replacing them with `.to(device)` and dynamically selecting the device resolved the issue while keeping the code compatible with GPU-enabled environments.

### Terraform IAM Role Creation

Initially, it appeared that only the role name was needed. However, IAM Roles cannot be created without an **Assume Role Policy**. Adding the required trust policy allowed Terraform to create the role successfully.

# Biggest Lessons Today

### AWS

Amazon S3 provides a cost-effective way to host static websites without provisioning servers by combining static website hosting with appropriate public read permissions.

### Azure

Azure Storage Static Website Hosting simplifies web hosting by automatically creating the `$web` container and exposing a dedicated static website endpoint.

### DevOps

`docker commit` is useful for preserving the current state of a running container during testing, although production images are generally built from Dockerfiles for reproducibility.

### MLOps

Writing device-aware PyTorch code with `torch.device()` and `.to(device)` enables the same training script to run unchanged on both CPU-only and GPU-enabled infrastructure.

### Terraform

An IAM Role differs from an IAM User because it requires a trust policy (`assume_role_policy`) at creation time to define who is permitted to assume the role.

### Kubernetes

A YAML manifest is the preferred way to create Kubernetes resources because it provides explicit, version-controlled configuration and supports repeatable deployments.
