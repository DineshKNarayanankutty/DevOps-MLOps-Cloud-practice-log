# MLOps — MLflow Champion/Challenger Promotion Gate

### Objective

Promote challenger model version `2` to the `production` alias only if its `f1_score` is strictly greater than the incumbent.

Current state:

```text
fraud-detector

v1 → production → f1_score 0.71
v2 → challenger → f1_score 0.82
```

Therefore:

```text
0.82 > 0.71
```

and v2 should be promoted.

### 1. Navigate to project

```bash
cd /root/code/monitoring
```

### 2. Inspect `promote.py`

The existing scaffold contained:

```python
from mlflow import MlflowClient

TRACKING_URI = "http://localhost:5000"
MODEL = "fraud-detector"
PROD_ALIAS = "production"
CHALLENGER_VERSION = "2"

client = MlflowClient(tracking_uri=TRACKING_URI)
```

The existing helper was:

```python
def f1_of(version: str) -> float:
    """Read the f1_score metric logged on a model version's run."""
    mv = client.get_model_version(MODEL, version)
    return client.get_run(mv.run_id).data.metrics["f1_score"]
```

### 3. Implement the promotion gate

The `main()` function was implemented as:

```python
def main() -> None:
    champion = client.get_model_version_by_alias(MODEL, PROD_ALIAS)
    champion_f1 = f1_of(champion.version)

    challenger_f1 = f1_of(CHALLENGER_VERSION)

    print(f"Champion version: {champion.version}, f1_score: {champion_f1}")
    print(
        f"Challenger version: {CHALLENGER_VERSION}, "
        f"f1_score: {challenger_f1}"
    )

    if challenger_f1 > champion_f1:
        client.set_registered_model_alias(
            MODEL,
            PROD_ALIAS,
            CHALLENGER_VERSION,
        )
        print(
            f"Promoted challenger version {CHALLENGER_VERSION} "
            f"to {PROD_ALIAS}"
        )
    else:
        print(
            f"Rejected challenger version {CHALLENGER_VERSION}; "
            f"{PROD_ALIAS} remains on version {champion.version}"
        )
```

The critical gate is:

```python
if challenger_f1 > champion_f1:
```

Promotion uses MLflow 3.x alias API:

```python
client.set_registered_model_alias(
    MODEL,
    PROD_ALIAS,
    CHALLENGER_VERSION,
)
```

### 4. Execute promotion

```bash
python3 promote.py
```

Expected result:

```text
Champion version: 1, f1_score: 0.71
Challenger version: 2, f1_score: 0.82
Promoted challenger version 2 to production
```

### 5. Verify production alias

```bash
python3 - <<'PY'

mv = client.get_model_version_by_alias(
```

### Key learning

```text
Drift-triggered retraining
        ↓
Challenger v2
        ↓
Evaluate F1
        ↓
Compare with production champion
        ↓
challenger F1 > champion F1 ?
        ↓
       YES
        ↓
production alias → v2
```

The important principle is **not**:

```text
new version → production
```

It is:

```text
better evaluated version → production
```

* NodePort: `30008`


```bash

```

```yaml

metadata:
  name: jenkins-deployment
  namespace: jenkins
  labels:
    app: jenkins
spec:
  replicas: 1
  selector:
    matchLabels:
      app: jenkins
  template:
    metadata:
      labels:
        app: jenkins
    spec:
      containers:
        - name: jenkins-container
          image: jenkins/jenkins

            - containerPort: 8080
```

# Terraform — CloudFormation Stack + DynamoDB

### Objective

Use Terraform to create:

```text
CloudFormation Stack
    devops-dynamodb-stack
             ↓
DynamoDB Table
    devops-cf-dynamodb-table
```

The task specifically required using:

* `main.tf`
* `variables.tf`
* provided `locals.tf`
* `outputs.tf`

and adding a lifecycle block that ignores `parameters`.

---

## 1. Existing `locals.tf`

The provided file contains:

```hcl
locals {
  cf_template_body = <<JSON
{
  "AWSTemplateFormatVersion": "2010-09-09",
  "Resources": {
    "MyDynamoDBTable": {
      "Type": "AWS::DynamoDB::Table",
      "Properties": {
        "TableName": "devops-cf-dynamodb-table",
        "AttributeDefinitions": [
          {
            "AttributeName": "ID",
            "AttributeType": "S"
          }
        ],
        "KeySchema": [
          {
            "AttributeName": "ID",
            "KeyType": "HASH"
          }
        ],
        "ProvisionedThroughput": {
          "ReadCapacityUnits": 5,
          "WriteCapacityUnits": 5
        }
      }
    }
  }
}
JSON
}
```

Important observation:

The CloudFormation template **does not define a `Parameters` section**.

Therefore, we should not try to pass a CloudFormation parameter such as:

```hcl
parameters = {
  DynamoDBTableName = ...
}
```

Instead, the required Terraform variable is used to substitute the table name in the existing template.

---

## 2. `variables.tf`

```hcl
variable "KKE_DYNAMODB_TABLE_NAME" {
  description = "DynamoDB table name"
  type        = string
}
```

## 3. `terraform.tfvars`

```hcl
KKE_DYNAMODB_TABLE_NAME = "devops-cf-dynamodb-table"
```

## 4. `main.tf`

```hcl
resource "aws_cloudformation_stack" "devops_dynamodb_stack" {
  name = "devops-dynamodb-stack"

  template_body = replace(
    local.cf_template_body,
    "\"TableName\": \"devops-cf-dynamodb-table\"",
    "\"TableName\": \"${var.KKE_DYNAMODB_TABLE_NAME}\""
  )

  lifecycle {
    ignore_changes = [
      parameters
    ]
  }
}
```

The important requirement:

```hcl
lifecycle {
  ignore_changes = [
    parameters
  ]
}
```

was included exactly as requested.

## 5. `outputs.tf`

```hcl
output "KKE_stack_name" {
  description = "CloudFormation stack name"
  value       = aws_cloudformation_stack.devops_dynamodb_stack.name
}
```
