# DevOps (Kubernetes)

## Task: Deploy MySQL with Persistent Storage, Secrets and NodePort

### Objective

Deploy a MySQL database on Kubernetes with persistent storage, Secret-based credentials, and a NodePort service.

### Requirements

```text
PersistentVolume: mysql-pv
Capacity: 250Mi
Access Mode: ReadWriteOnce
Reclaim Policy: Retain

PersistentVolumeClaim: mysql-pv-claim
Request: 250Mi

Deployment: mysql-deployment
Image: mysql:8.0
Replicas: 1
Mount Path: /var/lib/mysql

Service: mysql
Type: NodePort
Port: 3306
NodePort: 30007

Secrets:
mysql-root-pass
mysql-user-pass
mysql-db-url
```

### Step 1 — Create PersistentVolume

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: mysql-pv
spec:
  capacity:
    storage: 250Mi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /mnt/data/mysql
```

### Step 2 — Create PersistentVolumeClaim

The PVC was initially dynamically provisioned through the `local-path` StorageClass instead of binding to `mysql-pv`.

The issue was identified by:

```bash
kubectl get pv
kubectl get pvc
```

The manually created PV remained:

```text
mysql-pv   250Mi   RWO   Retain   Available
```

while the PVC was bound to a dynamically created PV.

To explicitly bind the PVC to `mysql-pv`, the configuration was updated to:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pv-claim
spec:
  storageClassName: ""
  volumeName: mysql-pv
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 250Mi
```

### Step 3 — Create MySQL Secrets

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: mysql-root-pass
type: Opaque
stringData:
  password: YUIidhb667
---
apiVersion: v1
kind: Secret
metadata:
  name: mysql-user-pass
type: Opaque
stringData:
  username: kodekloud_rin
  password: Rc5C9EyvbU
---
apiVersion: v1
kind: Secret
metadata:
  name: mysql-db-url
type: Opaque
stringData:
  database: kodekloud_db2
```

### Step 4 — Create MySQL Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8.0
          ports:
            - containerPort: 3306
          env:
            - name: MYSQL_ROOT_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mysql-root-pass
                  key: password
            - name: MYSQL_DATABASE
              valueFrom:
                secretKeyRef:
                  name: mysql-db-url
                  key: database
            - name: MYSQL_USER
              valueFrom:
                secretKeyRef:
                  name: mysql-user-pass
                  key: username
            - name: MYSQL_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mysql-user-pass
                  key: password
          volumeMounts:
            - name: mysql-storage
              mountPath: /var/lib/mysql
      volumes:
        - name: mysql-storage
          persistentVolumeClaim:
            claimName: mysql-pv-claim
```

### Step 5 — Create NodePort Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: mysql
spec:
  type: NodePort
  selector:
    app: mysql
  ports:
    - port: 3306
      targetPort: 3306
      nodePort: 30007
```

### Commands Used

```bash
kubectl apply -f mysql.yaml
kubectl get pv
kubectl get pvc
kubectl get secrets
kubectl get deployment mysql-deployment
kubectl get pods
kubectl get svc mysql
```

### Verification

The MySQL deployment was successfully running:

```text

```

Pod:

```text
mysql-deployment-6447b4c456-q69nm   1/1   Running   0
```

Service:

```text

```

### Key Learning

* PersistentVolumes provide cluster storage.
* PersistentVolumeClaims request storage from available PVs.
* A PVC can accidentally use a default StorageClass and dynamically provision another PV.
* `storageClassName: ""` and `volumeName: mysql-pv` can be used to explicitly bind to a manually created PV.
* Kubernetes Secrets can securely provide database credentials to containers.
* NodePort exposes a Kubernetes service through a port on each node.

# Terraform

## Task: Create IAM Role, Policy and Policy Attachment

### Objective

Create an AWS IAM role and policy using Terraform, then attach the policy to the role.

### Requirements

```text
IAM Role: datacenter-role
IAM Policy: datacenter-policy

Permission:
ec2:DescribeInstances

Outputs:
kke_iam_role_name
kke_iam_policy_name
```

### Files Used

```text
main.tf
variables.tf
terraform.tfvars
outputs.tf
```

### Step 1 — Define Variables

`variables.tf`:

```hcl
variable "KKE_ROLE_NAME" {
  description = "Name of the IAM role"
  type        = string
}

variable "KKE_POLICY_NAME" {
  description = "Name of the IAM policy"
  type        = string
}
```

### Step 2 — Provide Variable Values

`terraform.tfvars`:

```hcl
KKE_ROLE_NAME   = "datacenter-role"
KKE_POLICY_NAME = "datacenter-policy"
```

### Step 3 — Create IAM Role

`main.tf`:

```hcl
resource "aws_iam_role" "datacenter_role" {
  name = var.KKE_ROLE_NAME

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          Service = "ec2.amazonaws.com"
        }
        Action = "sts:AssumeRole"
      }
    ]
  })
}
```

### Step 4 — Create IAM Policy

```hcl
resource "aws_iam_policy" "datacenter_policy" {
  name        = var.KKE_POLICY_NAME
  description = "Allows listing EC2 instances"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect   = "Allow"
        Action   = "ec2:DescribeInstances"
        Resource = "*"
      }
    ]
  })
}
```

### Step 5 — Attach Policy to Role

```hcl
resource "aws_iam_role_policy_attachment" "datacenter_policy_attachment" {
  role       = aws_iam_role.datacenter_role.name
  policy_arn = aws_iam_policy.datacenter_policy.arn
}
```

### Step 6 — Create Outputs

`outputs.tf`:

```hcl
output "kke_iam_role_name" {
  description = "Name of the IAM role created"
  value       = aws_iam_role.datacenter_role.name
}

output "kke_iam_policy_name" {
  description = "Name of the IAM policy created"
  value       = aws_iam_policy.datacenter_policy.name
}
```

### Commands Used

```bash
terraform init
terraform fmt
terraform validate
terraform plan
terraform apply
```

Check outputs:

```bash
terraform output kke_iam_role_name
terraform output kke_iam_policy_name
```

AWS verification:

```bash
aws iam get-role --role-name datacenter-role
```

```bash
aws iam list-policies \
  --query "Policies[?PolicyName=='datacenter-policy']"
```

```bash
aws iam list-attached-role-policies \
  --role-name datacenter-role
```

### Key Learning

* IAM Roles provide identities that AWS services can assume.
* IAM Policies define permissions.
* `ec2:DescribeInstances` allows EC2 instance information to be listed/described.
* Terraform variables make IAM names configurable.
* `aws_iam_role_policy_attachment` connects the policy to the role.
* `jsonencode()` is useful for defining IAM JSON policies directly in Terraform.

# Linux

## Task: Install Squid and Configure Log Rotation

### Objective

Install the Squid package on all application servers and configure Squid log rotation to run monthly while retaining only three rotated logs.

### Step 1 — Install Squid and logrotate

On each application server:

```bash
yum install -y squid logrotate
```

Verify Squid:

```bash
rpm -q squid
```

Verify logrotate:

```bash
rpm -q logrotate
```

### Step 2 — Check Existing Squid Logrotate Configuration

The existing configuration was checked with:

```bash
cat /etc/logrotate.d/squid
```

The original configuration contained:

```text
/var/log/squid/*.log {
    weekly
    rotate 5
    compress
    delaycompress
    notifempty
    missingok
    nocreate
    sharedscripts
    postrotate
      /usr/sbin/squid -k rotate 2>/dev/null
    endscript
}
```

### Step 3 — Update Rotation Frequency and Retention

Changed:

```text
weekly
rotate 5
```

to:

```text
monthly
rotate 3
```

The configuration was updated using:

```bash
sed -i 's/weekly/monthly/; s/rotate 5/rotate 3/' /etc/logrotate.d/squid
```

### Step 4 — Verify Configuration

```bash
cat /etc/logrotate.d/squid
```

Final important settings:

```text
monthly
rotate 3
compress
delaycompress
```

The existing Squid log path remained:

```text
/var/log/squid/*.log
```

### Step 5 — Test logrotate

Initially:

```bash
sudo logrotate -d /etc/logrotate.conf
```

returned:

```text
sudo: logrotate: command not found
```

Installed the missing package:

```bash
yum install -y logrotate
```

Then tested:

```bash
logrotate -d /etc/logrotate.conf
```

### Key Learning

* `logrotate` prevents log files from growing indefinitely.
* `monthly` controls rotation frequency.
* `rotate 3` retains only three rotated logs.
* `compress` reduces storage usage by compressing rotated logs.
* Existing logrotate configurations should be modified instead of creating duplicate configurations.
* Required packages should be verified before running configuration/testing commands.
* The same configuration needs to be applied across all app servers.
