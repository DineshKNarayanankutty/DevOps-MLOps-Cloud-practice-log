## Tasks Performed

### Created KMS Key

Configuration:

```text

Symmetric

Usage:
Encrypt / Decrypt

Alias:

```

---

### Retrieved Key Information

Commands:

```bash
aws kms list-aliases

aws kms describe-key \
    --key-id alias/devops-KMS-Key
```

---

### Encrypted Sensitive File

Input:

```text
/root/SensitiveData.txt
```

Command:

```bash
aws kms encrypt \
    --key-id alias/devops-KMS-Key \
    --plaintext fileb:///root/SensitiveData.txt \
    --query CiphertextBlob \
    --output text | base64 --decode \
    > /root/EncryptedData.bin
```

---

### Decrypted File

Command:

```bash
aws kms decrypt \
    --ciphertext-blob fileb:///root/EncryptedData.bin \
    --query Plaintext \
    --output text | base64 --decode \
    > /root/DecryptedData.txt
```

---

### Verification

Compared both files:

```bash
diff /root/SensitiveData.txt \
     /root/DecryptedData.txt
```

No output indicates both files are identical.

---

## Encryption Workflow

```text
SensitiveData.txt
        │
        ▼
AWS KMS
(devops-KMS-Key)
        │
Encrypt
        ▼
CiphertextBlob
(Base64)
        │
Base64 Decode
        ▼
EncryptedData.bin
        │
Decrypt
        ▼
Plaintext
(Base64)
        │
Base64 Decode
        ▼
DecryptedData.txt
```

---

## Key Learning

AWS KMS does **not** store application files.

Instead it securely stores encryption keys and performs cryptographic operations.

Applications remain responsible for storing encrypted files.

# MLOps

# Building a Feature Store with Feast

## Objective

Initialize a Feast Feature Repository, register feature definitions, generate a **point-in-time correct training dataset**, and visualize the repository through the Feast UI.

This task introduced one of the most important concepts in production MLOps: **Feature Stores**.

---

## Why Feature Stores?

In many ML projects, the same feature engineering logic gets implemented multiple times:

```text
Training Script

↓

Feature Engineering
```

Later,

```text
Inference Service

↓

Feature Engineering
```

If the implementations differ even slightly, the model receives different features during inference than it saw during training. This is known as **training-serving skew**.

A Feature Store solves this by centralizing feature definitions.

```text
Raw Data
      │
      ▼
Feature Store
      │
      ├── Training
      └── Online Serving
```

Both training and inference use the same feature definitions.

---


---

---

## Step 3: Generate a Point-in-Time Training Set

The supplied script contained:

```python
training_df = entity_df
```

This was incorrect because it ignored the Feature Store.

It was replaced with:

```python
training_df = (
    store.get_historical_features(
        entity_df=entity_df,
        features=[
            "driver_hourly_stats:conv_rate",
            "driver_hourly_stats:acc_rate",
            "driver_hourly_stats:avg_daily_trips",
        ],
    )
    .to_df()
)
```

---

### What `get_historical_features()` Does

The source data only contained:

```text
driver_id

event_timestamp
```

Example:

| driver_id | event_timestamp  |
| --------- | ---------------- |
| 1001      | 2025-05-10 09:00 |
| 1002      | 2025-05-10 09:15 |

These values alone are not enough to train a fraud detection model.

Feast performs a **point-in-time join**, retrieving feature values exactly as they existed at the given timestamp.

After retrieval:

| driver_id | event_timestamp | conv_rate | acc_rate | avg_daily_trips |
| --------- | --------------- | --------- | -------- | --------------- |
| 1001      | 09:00           | 0.72      | 0.95     | 14              |
| 1002      | 09:15           | 0.61      | 0.89     | 8               |

---

### Why Point-in-Time Joins Matter

Suppose today's feature value is:

```text
Conversion Rate

0.95
```

But six months ago it was:

```text
0.42
```

If the model is being trained on historical fraud events from six months ago, using today's value (0.95) would expose information that **did not exist at prediction time**.

This is called **data leakage (label leakage)**.

Feast prevents this by retrieving:

```text
Feature Value

AS OF

event_timestamp
```

instead of the latest value.

This guarantees that the training data reflects only the information available when each event originally occurred.

# Biggest Lessons Today

### AWS

AWS KMS is responsible for securely managing encryption keys and performing cryptographic operations. It does not store or manage application files.

### Azure

Azure Table Storage is a NoSQL key-value store where application data is organized as entities identified by `PartitionKey` and `RowKey`, making it suitable for scalable application metadata and lightweight transactional data.

### DevOps

Dockerfiles define repeatable image builds. By embedding application installation and configuration into the image, deployments become consistent across development, testing, and production.

### MLOps

A Feature Store such as Feast ensures that the same feature definitions are reused during both model training and online inference. Point-in-time feature retrieval prevents data leakage by ensuring each training example only includes feature values that existed when that event occurred.

### Kubernetes

Namespaces provide resource isolation within a shared cluster, allowing teams and environments to operate independently while using the same Kubernetes infrastructure.
