# Kubernetes

## Task: Create Persistent Volume, PVC, Pod and NodePort Service

### Objective

Create Kubernetes persistent storage for a web application, mount it into an Apache HTTPD container, and expose the application through a NodePort service.

### Requirements

* PersistentVolume: `pv-xfusion`
* Storage class: `manual`
* PV capacity: `5Gi`
* Access mode: `ReadWriteOnce`
* Volume type: `hostPath`
* Host path: `/mnt/itadmin`
* PersistentVolumeClaim: `pvc-xfusion`
* PVC request: `1Gi`
* Pod: `pod-xfusion`
* Container: `container-xfusion`
* Image: `httpd:latest`
* Document root: `/usr/local/apache2/htdocs`
* Service: `web-xfusion`
* Service type: `NodePort`
* NodePort: `30008`

### Code Used

Created a single YAML manifest containing all four resources:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-xfusion
spec:
  storageClassName: manual
  capacity:
    storage: 5Gi
  accessModes:
    - ReadWriteOnce
  hostPath:
    path: /mnt/itadmin

---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-xfusion
spec:
  storageClassName: manual
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi

---
apiVersion: v1
kind: Pod
metadata:
  name: pod-xfusion
  labels:
    app: xfusion
spec:
  containers:
    - name: container-xfusion
      image: httpd:latest
      volumeMounts:
        - name: xfusion-storage
          mountPath: /usr/local/apache2/htdocs
  volumes:
    - name: xfusion-storage
      persistentVolumeClaim:
        claimName: pvc-xfusion

---
apiVersion: v1
kind: Service
metadata:
  name: web-xfusion
spec:
  type: NodePort
  selector:
    app: xfusion
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30008
```

### Commands Used

Create/apply the resources:

```bash
kubectl apply -f xfusion.yaml
```

Check PV:

```bash
kubectl get pv pv-xfusion
```

Check PVC:

```bash
kubectl get pvc pvc-xfusion
```

Check Pod:

```bash
kubectl get pod pod-xfusion
```

Check Service:

```bash
kubectl get svc web-xfusion
```

Detailed troubleshooting/verification:

```bash
kubectl describe pv pv-xfusion
kubectl describe pvc pvc-xfusion
kubectl describe pod pod-xfusion
kubectl describe svc web-xfusion
```

### Key Learning

* A **PersistentVolume** represents available storage.
* A **PersistentVolumeClaim** requests storage from a PV.
* The PVC requested `1Gi`, while the PV provided `5Gi`.
* `ReadWriteOnce` controls how the volume can be mounted.
* `hostPath` stores data on the Kubernetes node.
* A PVC is mounted into the Pod through `volumes` and `volumeMounts`.
* `NodePort` exposes the application externally through port `30008`.

### Whole Code

```python
"""BentoML service exposing the fraud-detection RandomForest.

Loads `fraud_detector:latest` from the BentoML model store (saved at
startup) and serves it with the modern `@bentoml.service` class API:
  - POST /predict           — score one transaction.
  - POST /last_predictions  — audit log of every POST /predict
                              handled since the server booted.

`bentoml serve service:FraudService` starts the HTTP server on port
3000 and auto-generates a Swagger UI at the server's root — the
primary GUI surface for this lab.
"""
from typing import Any, Dict, List

import bentoml
import numpy as np


@bentoml.service(name="fraud_service")
class FraudService:
    # Declare the model dependency from the store; BentoML resolves it
    # and makes it available for loading.
    bento_model = bentoml.models.BentoModel("fraud_detector:latest")

    def __init__(self) -> None:
        self.model = bentoml.sklearn.load_model(self.bento_model)
        self._history: List[Dict[str, Any]] = []

    @bentoml.api
    def predict(
        self, amount: float, hour: int, num_tx_past_day: int
    ) -> Dict[str, Any]:
        features = np.array([[amount, hour, num_tx_past_day]])

        is_fraud = int(self.model.predict(features)[0])

        self._history.append({
            "amount": amount,
            "hour": hour,
            "num_tx_past_day": num_tx_past_day,
            "is_fraud": is_fraud,
        })

        return {"is_fraud": is_fraud}

    @bentoml.api
    def last_predictions(self) -> Dict[str, Any]:
        return {"count": len(self._history), "predictions": self._history}
```

## Task: Create Kinesis Data Stream and CloudWatch Alarm

### Objective

---

## `main.tf`

Code used:

```hcl
terraform {
  required_providers {
    aws = {
      source = "hashicorp/aws"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_kinesis_stream" "nautilus_kinesis_stream" {
  name             = "nautilus-kinesis-stream"
  shard_count      = 1
  retention_period = 24

  shard_level_metrics = [
    "WriteProvisionedThroughputExceeded"
  ]
}

resource "aws_cloudwatch_metric_alarm" "nautilus_kinesis_alarm" {
  alarm_name        = "nautilus-kinesis-alarm"
  alarm_description = "Alarm when Kinesis write throughput exceeds provisioned limits"

  namespace           = "AWS/Kinesis"
  metric_name         = "WriteProvisionedThroughputExceeded"
  statistic           = "Sum"
  period              = 60
  evaluation_periods  = 1
  threshold           = 1
  comparison_operator = "GreaterThanThreshold"

  dimensions = {
    StreamName = aws_kinesis_stream.nautilus_kinesis_stream.name
  }

  treat_missing_data = "notBreaching"
}
```

# Linux

## Task: Troubleshoot and Restore MariaDB

### Objective

Restore the MariaDB service on the Nautilus database server `stdb01` after the service repeatedly failed to start.

### Server

```text
stdb01
```

### Initial Check

Checked MariaDB status:

```bash
sudo systemctl status mariadb -l
```

Result:

```text
Active: failed (Result: exit-code)
```

MariaDB was not listening on port `3306`.

Checked:

```bash
sudo ss -tlnp | grep 3306
```

No output was returned.

---

## Initial Log Investigation

Checked MariaDB journal:

```bash
journalctl -u mariadb --no-pager -n 50
```

The service was failing with:

```text
Main process exited, code=exited, status=1/FAILURE
```

The journal also showed that the database was already initialized:

```text
Database MariaDB is probably initialized in /var/lib/mysql already, nothing is done.
```

Therefore, the database directory should **not** be reinitialized or deleted.

---

## Root Cause

Checked the MariaDB log:

```bash
sudo tail -100 /var/log/mariadb/mariadb.log
```

The critical error was:

```text
[ERROR] mariadbd: Can't create/write to file '/run/mariadb/mariadb.pid'
(Errcode: 13 "Permission denied")
```

followed by:

```text
[ERROR] Can't start server: can't create PID file: Permission denied
```

### Root Cause

MariaDB could initialize InnoDB and access `/var/lib/mysql`, but it could not create its PID file under:

```text
/run/mariadb/mariadb.pid
```

because of a permissions problem with the runtime directory.

---

## Verification Performed

Checked MariaDB data directory:

```bash
sudo ls -la /var/lib/mysql | head -30
```

Ownership was:

```text
mysql mysql
```

Checked directory ownership:

```bash
sudo stat -c '%U:%G %a %n' /var/lib/mysql
```

Result:

```text
mysql:mysql 755 /var/lib/mysql
```

Checked disk space:

```bash
df -h /var/lib/mysql
```

Disk usage was only around:

```text
29%
```

Checked inode usage:

```bash
df -i /var/lib/mysql
```

Inode usage was around:

```text
11%
```

Therefore:

* Data directory ownership was not the issue.
* Disk space was not the issue.
* Inodes were not the issue.
* Port `3306` was not occupied.
* The actual failure was `/run/mariadb` permissions.

---

## Fix Applied

Created the runtime directory:

```bash
sudo mkdir -p /run/mariadb
```

Set the correct ownership:

```bash
sudo chown mysql:mysql /run/mariadb
```

Set directory permissions:

```bash
sudo chmod 755 /run/mariadb
```

Restore SELinux context:

```bash
sudo restorecon -Rv /run/mariadb
```

Restart MariaDB:

```bash
sudo systemctl restart mariadb
```

Check status:

```bash
sudo systemctl status mariadb -l
```

Verify listening port:

```bash
sudo ss -ltnp | grep 3306
```

Verify database connectivity:

```bash
sudo mysql -e "SELECT VERSION();"
```

### Important Troubleshooting Lesson

The initial assumption could have been that MariaDB was simply stopped, but:

```text
systemctl status mariadb
```

showed:

```text
Active: failed
```

The correct troubleshooting path was:

```text
systemctl status
       ↓
journalctl
       ↓
MariaDB error log
       ↓
identify PID-file permission error
       ↓
inspect /run/mariadb
       ↓
correct ownership/permissions/context
       ↓
restart MariaDB
```

Also, we **did not delete `/var/lib/mysql` or reinitialize MariaDB**, because the existing database was already initialized.

# Overall Key Learnings – Day 60

## Kubernetes

* PersistentVolumes provide persistent storage to Kubernetes workloads.
* PVCs request storage from available PVs.
* A Pod can mount a PVC into a container using `volumeMounts`.
* NodePort exposes a Kubernetes application externally.

## MLOps / BentoML

* BentoML model store allows registered models to be loaded by a serving application.
* `@bentoml.service` is the modern service API.
* `@bentoml.api` exposes prediction methods as HTTP endpoints.
* A prediction API should transform incoming request data into the feature format expected by the model.
* Prediction history can be maintained for simple auditing.

## Terraform / AWS

* Terraform can provision streaming infrastructure and monitoring together.
* Kinesis shard-level metrics provide visibility into throughput issues.
* CloudWatch alarms can detect `WriteProvisionedThroughputExceeded`.
* Terraform outputs make important resource names easily accessible.

## Linux

* `systemctl status` identifies service state.
* `journalctl` provides systemd service logs.
* Application-specific logs often reveal the actual root cause.
* `ss` helps verify whether a service is listening on the expected port.
* Permission errors should be investigated at the exact file/directory mentioned in the log.
* Never delete or reinitialize a database directory during troubleshooting unless you have confirmed that the existing data is disposable.
