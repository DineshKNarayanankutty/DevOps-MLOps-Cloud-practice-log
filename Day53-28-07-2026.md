# DevOps & Kubernetes

## Task 1: Troubleshoot and Fix Nginx + PHP-FPM Kubernetes Pod

### Objective

The Nginx + PHP-FPM application stopped working after deployment. The objective was to investigate the Kubernetes resources, identify the configuration issue, restore the application, and deploy the PHP application successfully.

---

## Environment

* Platform: Kubernetes
* Pod: `nginx-phpfpm`
* ConfigMap: `nginx-config`

---

## Step 1: Export Existing Resources

Before making any changes, exported the existing Pod and ConfigMap for analysis.

```bash
kubectl get pod nginx-phpfpm -o yaml > pod.yaml

kubectl get cm nginx-config -o yaml > configmap.yaml
```

---

## Step 2: Investigate the Configuration

Compared:

* Pod specification
* ConfigMap
* Volume mounts
* Nginx configuration
* PHP-FPM configuration

---

## Root Cause

Discovered that both containers were mounting the shared volume at different filesystem paths.

### PHP-FPM Container

```yaml
volumeMounts:
- mountPath: /usr/share/nginx/html
  name: shared-files
```

### Nginx Container

```yaml
volumeMounts:
- mountPath: /var/www/html
  name: shared-files
```

Nginx configuration contained:

```nginx
root /var/www/html;
```

Because PHP-FPM expected application files under `/usr/share/nginx/html` while Nginx served them from `/var/www/html`, PHP-FPM could not locate the requested scripts. This resulted in **404 File not found** errors whenever Nginx forwarded PHP requests.

---

## Step 3: Correct the Pod Manifest

Modified the Pod manifest so that both containers mounted the shared volume at the same document root.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-phpfpm
  labels:
    app: php-app

spec:
  volumes:
    - name: shared-files
      emptyDir: {}

    - name: nginx-config-volume
      configMap:
        name: nginx-config

  containers:

    - name: php-fpm-container
      image: php:7.2-fpm-alpine
      volumeMounts:
        - name: shared-files
          mountPath: /var/www/html

    - name: nginx-container
      image: nginx:latest
      volumeMounts:
        - name: shared-files
          mountPath: /var/www/html
        - name: nginx-config-volume
          mountPath: /etc/nginx/nginx.conf
          subPath: nginx.conf
```

---

## Step 4: Recreate the Pod

Deleted the existing Pod.

```bash
kubectl delete pod nginx-phpfpm --force --grace-period=0
```

Applied the corrected manifest.

```bash
kubectl apply -f pod.yaml
```

Waited until the Pod reached the Running state.

```bash
kubectl get pod nginx-phpfpm -w
```

---

## Step 5: Deploy the PHP Application

Copied the application file into the shared document root.

```bash
kubectl cp /home/thor/index.php nginx-phpfpm:/var/www/html/ -c nginx-container
```

---

## Step 6: Verification

Verified that the file existed inside both containers.

```bash
kubectl exec nginx-phpfpm -c nginx-container -- ls -l /var/www/html/index.php

kubectl exec nginx-phpfpm -c php-fpm-container -- ls -l /var/www/html/index.php
```

Opened the Website button and confirmed the PHP application loaded successfully.

---

## Key Learning

* Export Kubernetes resources before making changes.
* Verify ConfigMaps, volume mounts, and application paths together.
* Multi-container Pods using shared volumes must mount them at compatible paths.
* Standalone Pods must be recreated after modifying their manifests.

# Linux

## Configure Password-less Sudo Access

## Objective

Provide administrative privileges to user **mark** on all application servers without requiring a password.

---

## Environment

* App Server 1
* App Server 2
* App Server 3

---

## Step 1: Connect to Each Server

```bash
ssh tony@appserver1
```

Repeated the same procedure for all application servers.

---

## Step 2: Switch to Root

```bash
sudo su -
```

---

## Step 3: Grant Password-less Sudo

Created a dedicated sudoers file.

```bash
echo "mark ALL=(ALL) NOPASSWD: ALL" > /etc/sudoers.d/mark
```

Assigned the correct permissions.

```bash
chmod 440 /etc/sudoers.d/mark
```

---

## Step 4: Verify Configuration

Checked the sudoers entry.

```bash
cat /etc/sudoers.d/mark
```

Verified sudo access.

```bash
su - mark

sudo whoami
```

Expected output:

```text
root
```

Repeated the same configuration on all application servers.

---

## Key Learning

* Use `/etc/sudoers.d/` instead of editing `/etc/sudoers` directly.
* Always set sudoers file permissions to `440`.
* `NOPASSWD` enables password-less administrative access.

# MLOps

## Task: Build a CPU-Only PyTorch Docker Image

### Objective

The provided Dockerfile attempted to install the GPU version of PyTorch and required CUDA during container startup. Since the lab host is CPU-only, the Dockerfile needed to be updated to build and run successfully.

---

## Project Location

```text
/root/code/dl-docker/
```

---

## Initial Problems

The Dockerfile contained two issues:

### 1. GPU Package Repository

```dockerfile
--index-url https://download.pytorch.org/whl/gpu
```

The lab environment does not provide GPU hardware.

---

### 2. Runtime Validation

The container executed:

```python
assert torch.cuda.is_available(), "CUDA required"
```

This caused the container to exit immediately because CUDA was unavailable.

---

## Corrected Dockerfile

```dockerfile
FROM python:3.11-slim

WORKDIR /app

RUN pip install --no-cache-dir \
    --index-url https://download.pytorch.org/whl/cpu \
    torch

CMD ["python3", "-c", "import torch; print(torch.__version__, 'cuda?', torch.cuda.is_available())"]
```

---

## Step 1: Build the Image

```bash
cd /root/code/dl-docker

docker build -t dl-trainer:v1 .
```

Verified that the build completed successfully.

---

## Step 2: Verify the Image

```bash
docker images dl-trainer:v1
```

Confirmed that the Docker image was created.

---

## Step 3: Run the Container

```bash
docker run --rm dl-trainer:v1
```

Expected output:

```text
2.x.x+cpu cuda? False
```

This verified that:

* CPU-only PyTorch was installed.
* CUDA detection correctly returned `False`.
* The container exited successfully with status code `0`.

---

## Verification Commands

```bash
docker build -t dl-trainer:v1 .

docker images dl-trainer:v1

docker run --rm dl-trainer:v1
```

# Key Learnings

## DevOps & Kubernetes

* Troubleshoot Kubernetes issues by exporting and inspecting resource manifests before making changes.
* In multi-container Pods, ensure shared volumes are mounted consistently across all containers.
* Recreate standalone Pods after updating their manifests.
* Use `/etc/sudoers.d/` to safely grant password-less administrative access.
* Validate configuration changes by testing the affected user account.

## MLOps

* Choose the correct software distribution for the target hardware (CPU vs. GPU).
* Use the CPU-specific PyTorch wheel index on systems without GPU support.
* Container startup commands should verify functionality without assuming CUDA availability.
* Validate Docker images by confirming successful build, image creation, and expected runtime output before considering the task complete.
