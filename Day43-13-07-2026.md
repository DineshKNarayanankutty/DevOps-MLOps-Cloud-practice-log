# MLOps

# Feast Online Feature Materialization and Online Feature Retrieval

## Objective

Populate Feast's online feature store from the offline Parquet source, then retrieve real-time features using `get_online_features()` to simulate an online inference request.

This exercise demonstrated how Feast bridges **offline training data** and **online serving data** while maintaining consistent feature definitions.

---

## Project Structure

```text
feature_repo/

├── feature_store.yaml
├── features.py
├── materialize.sh
├── fetch_features.py
├── data/
│   ├── transactions.parquet
│   ├── registry.db
│   └── online_store.db
```

---

## Problem Identified

The script contained:

```bash
END_DATE="1970-12-31T00:00:00"
```

However, the source dataset contained event timestamps beginning from:

```text
2024-01-01
```

Running:

```bash
./materialize.sh
```

produced:

```text
0 rows materialized
```

because no feature records existed before the specified end date.

---

## Fix Applied

Updated:

```bash
END_DATE="2024-12-31T23:59:59"
```

---

## Materialization

Executed:

```bash
chmod +x materialize.sh

./materialize.sh
```

Feast copied feature values from the offline store into the online SQLite store.

---

## Online Store Verification

Verified:

```bash
ls -lh data/online_store.db
```

Confirmed the database size exceeded the SQLite header, indicating successful materialization.

---

## Online Feature Retrieval

Implemented:

```python
result = (
    store.get_online_features(
        features=[
            "customer_transaction_features:amount",
            "customer_transaction_features:hour",
            "customer_transaction_features:num_tx_past_day",
        ],
        entity_rows=[
            {"customer_id": i}
            for i in range(1, 6)
        ],
    )
    .to_dict()
)
```

---

## Generated Output

Executed:

```bash
python3 fetch_features.py
```

Generated:

```text
online_features.json
```

containing:

```text
customer_id

amount

hour

num_tx_past_day
```

Verified that at least one customer had a non-null `amount` value.

---

## End-to-End Feature Flow

```text

        │
        ▼

(customer_transaction_features)
        │
        ▼

        │
        ▼

        │
```

## Key Learning

Feast separates:

```text
Offline Store
```

used for **training datasets** from:

```text
Online Store
```

used for **low-latency inference**.

Materialization synchronizes feature values from the offline source into the online store, allowing production applications to fetch features in milliseconds using only entity keys.

# Linux

# Updating the Message of the Day (MOTD)

## Objective

Deploy a standardized login banner to all Nautilus application servers to satisfy organizational security and compliance requirements.

---

## Source Banner

Located on the jump host:

```text
/home/thor/nautilus_banner
```

---

## Initial Issue

Attempted:

```bash
sudo cp /home/thor/nautilus_banner /etc/motd
```

Result:

```text
cp: cannot stat '/home/thor/nautilus_banner'
```

Reason:

The banner file existed **only on the jump host**, not on the application servers.

---

## Solution

Copied the banner from the jump host to each server:

```bash
scp /home/thor/nautilus_banner tony@stapp01:/tmp/

scp /home/thor/nautilus_banner tony@stapp02:/tmp/

scp /home/thor/nautilus_banner tony@stapp03:/tmp/
```

On each server:

```bash
sudo cp /tmp/nautilus_banner /etc/motd
```

---

## Verification

Checked:

```bash
cat /etc/motd
```

Reconnected to the servers and confirmed the banner appeared immediately after login.

---

## Banner Deployment Flow

```text
Jump Host
      │
Approved Banner
      │
      ▼
Copy via SCP
      │
      ├── stapp01
      ├── stapp02
      └── stapp03
      │
      ▼
/etc/motd
      │
      ▼
Displayed on Login
```

---

## Key Learning

The Linux **Message of the Day (MOTD)** is stored in `/etc/motd` and is displayed after successful user authentication. It is commonly used to present legal notices, security warnings, maintenance information, or organizational policies.

# Issues Encountered Today

### Feast Materialization

* The materialization script used an end date (`1970-12-31`) that preceded all transaction timestamps, resulting in zero rows being written to the online store.
* Correcting the end date to a value on or after `2024-01-01` allowed the online SQLite store to be populated successfully.

### Linux MOTD

* The banner file was unavailable on the application servers because it resided only on the jump host.
* Resolved by securely copying the approved banner to each server before updating `/etc/motd`.

# Biggest Lessons Today

### AWS

A private EKS endpoint limits API access to trusted networks, strengthening cluster security while maintaining high availability through multi-AZ deployment.

### Azure

Application Gateway provides Layer-7 routing, making it ideal for HTTP/HTTPS traffic management and backend health monitoring.

### DevOps

Docker port mapping decouples the host's networking from the container's internal ports, simplifying application exposure.

### MLOps

Feature stores separate offline training data from online serving data. Materialization is the critical synchronization step that makes historical features available for real-time inference with low latency.

### Linux

Administrative files available on a jump host are not automatically present on managed servers. Tools like `scp` securely distribute configuration files before they are applied.

### Kubernetes

Rolling updates enable continuous delivery by gradually replacing application Pods, minimizing service interruption while deploying new application versions.
