# 1. DevOps (Kubernetes) — Troubleshooting Python Flask Application

## Task

A Python Flask application was already deployed on a Kubernetes cluster, but the application was not coming up correctly.

The requirement was:

* Deployment name: `python-deployment-devops`
* Required image: `poroko/flask-demo-app`
* Flask application's default port: `5000`
* Service `targetPort`: `5000`
* Service `nodePort`: `32345`

The Deployment and Service already existed, so the task was to **investigate the existing configuration rather than create everything from scratch**.

---

## Step 1 — Check the existing Deployment

First check whether the Deployment exists:

```bash
kubectl get deployment python-deployment-devops
```

Then inspect its detailed configuration:

```bash
kubectl describe deployment python-deployment-devops
```

Check the Pods created by the Deployment:

```bash
kubectl get pods
```

For more information:

```bash
kubectl get pods -o wide
```

### What we were looking for

When an application is not coming up, check:

1. Is the Deployment available?
2. Are Pods running?
3. Is the image correct?
4. Are Pods restarting?
5. Is the application listening on the expected port?

---

## Step 2 — Check the container image

Inspect the Deployment:

```bash
kubectl get deployment python-deployment-devops -o yaml
```

We found an image mismatch.

The Deployment had:

```text
poroko/flask-app-demo
```

But the task required:

```text
poroko/flask-demo-app
```

### Correct image

```yaml
image: poroko/flask-demo-app
```

The image name is important because Kubernetes uses the exact image reference when creating the container.

A small difference such as:

```text
flask-app-demo
```

vs.

```text
flask-demo-app
```

refers to two different image names.

---

## Step 3 — Check the Service

List the Services:

```bash
kubectl get svc
```

Get detailed information:

```bash
kubectl describe svc <service-name>
```

Or inspect the complete YAML:

```bash
kubectl get svc <service-name> -o yaml
```

We found the Service port configuration had a mismatch.

The application was a Flask application using its default port:

```text
5000
```

But the Service was forwarding traffic to:

```text
8080
```

### Incorrect

```yaml
targetPort: 8080
```

### Correct

```yaml
targetPort: 5000
```

The required NodePort was:

```yaml
nodePort: 32345
```

So the Service needed to expose:

```yaml
ports:
  - port: 5000
    targetPort: 5000
    nodePort: 32345
```

---

## Step 4 — Understand the Kubernetes port flow

This is important to remember for future troubleshooting.

```text
Client
   |
   | NodeIP:32345
   v
NodePort Service
   |
   | targetPort:5000
   v
Pod
   |
   | Flask application
   |
   +---- listening on 5000
```

There are three concepts:

### `nodePort`

The port exposed on the Kubernetes node.

```text
32345
```

The user accesses:

```text
http://<NODE-IP>:32345
```

### `port`

The Service's internal port.

For example:

```yaml
port: 5000
```

### `targetPort`

The port on the actual application container.

```yaml
targetPort: 5000
```

The important relationship here was:

```text
nodePort 32345
       ↓
Service
       ↓
targetPort 5000
       ↓
Flask application :5000
```

---

The Deployment can be edited with:

```bash
kubectl edit deployment python-deployment-devops
```

Find:

```yaml
containers:
  - image: poroko/flask-app-demo
```

Change it to:

```yaml
containers:
  - image: poroko/flask-demo-app
```

Save and exit.

Alternatively, if appropriate for the existing Deployment:

```bash
kubectl set image deployment/python-deployment-devops \
  <container-name>=poroko/flask-demo-app
```

Then monitor the rollout:

```bash
kubectl rollout status deployment/python-deployment-devops
```

---

## Step 6 — Correct the Service

Edit the existing Service:

```bash
kubectl edit svc <service-name>
```

Ensure the port section contains:

```yaml
ports:
  - port: 5000
    targetPort: 5000
    nodePort: 32345
```

Do not create another Service if the existing Service is supposed to be fixed.

```bash
kubectl get pods
```

Expected:

For future application problems, follow this order:

```text

        ↓

        ↓
```

### Key learning

A Kubernetes Service does not magically make an application available. The traffic must ultimately reach the correct port where the application is listening.

Today's issue demonstrated two common mistakes:

```text
Wrong image

        ↓
Correct image
poroko/flask-demo-app
```

and:

```text
Wrong targetPort
8080
        ↓
Correct targetPort
5000
```

# 2. Docker — Multi-Model Flask Application with Nginx

## Task

The ML platform contained three Flask services:

```text
fraud
churn
recommend
```

`fraud` and `churn` were already integrated with Docker Compose and Nginx.

The `recommend` application already existed:

```text
recommend/
├── app.py
└── Dockerfile
```

But it wasn't included in:

```text
docker-compose.yml
```

or:

```text
nginx.conf
```

The objective was to integrate it without changing the existing working services.

---

# Step 1 — Navigate to the project

```bash
cd /root/code/serving/multi-model/
```

Check the directory:

```bash
ls
```

Expected:

```text
fraud
churn
recommend
docker-compose.yml
nginx.conf
```

Check the recommend directory:

```bash
ls recommend
```

Expected:

```text
app.py
Dockerfile
```

---

# Step 2 — Inspect the existing Docker Compose file

```bash
cat docker-compose.yml
```

The existing file contained services similar to:

```yaml
services:
  fraud:
    ...

  churn:
    ...

  nginx:
    ...
```

The `recommend` service was missing.

---

# Step 3 — Model the new service on the existing services

Add:

```yaml
recommend:
  build: ./recommend
  container_name: mm-recommend
```

Important details:

```text
build: ./recommend
```

means Docker Compose builds the image using the Dockerfile inside:

```text
/root/code/serving/multi-model/recommend/
```

The required container name was:

```text
mm-recommend
```

---

# Step 4 — Inspect Nginx configuration

```bash
cat nginx.conf
```

Existing routes included:

```text
/fraud/
/churn/
```

The `/recommend/` route was missing.

---

# Step 5 — Add the recommend upstream

Add:

```nginx
upstream recommend {
    server recommend:5000;
}
```

Here:

```text
recommend
```

is the Docker Compose service name.

Docker Compose provides internal DNS, so Nginx can resolve:

```text
recommend
```

to the recommend container.

The Flask application is listening on:

```text
5000
```

Therefore:

```nginx
server recommend:5000;
```

---

# Step 6 — Add the Nginx location

Add:

```nginx
location /recommend/ {
    proxy_pass http://recommend/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

The request flow becomes:

```text
POST /recommend/predict
        ↓
Nginx :8085
        ↓
upstream recommend
        ↓
recommend:5000
        ↓
Flask /predict
```

---

# Step 7 — Start the stack

```bash
docker compose up -d
```

The important point here is that we did **not** need to manually build the recommend image first.

Docker Compose reads:

```yaml
build: ./recommend
```

and builds the image automatically.

# 3. Terraform — AWS S3 Lifecycle Management

## Task

Created an S3 bucket using Terraform and configured:

```text
Bucket
  ↓
Versioning
  ↓
Lifecycle rule
  ├── 30 days → STANDARD_IA
  └── 365 days → Expiration
```

Required bucket:

```text
datacenter-lifecycle-7584
```

Required lifecycle rule:

```text
datacenter-lifecycle-rule
```

---

# Step 1 — Check Terraform files

```bash
ls
```

The requirement specifically stated that the S3 resources should be placed in:

```text
main.tf
```

and the output in:

```text
outputs.tf
```

Do not create another Terraform file for this task.

---

# Step 2 — Create the S3 bucket

In `main.tf`:

```hcl
resource "aws_s3_bucket" "lifecycle_bucket" {
  bucket = "datacenter-lifecycle-7584"
}
```

---

# Step 3 — Enable S3 Versioning

Add:

```hcl
resource "aws_s3_bucket_versioning" "lifecycle_bucket_versioning" {
  bucket = aws_s3_bucket.lifecycle_bucket.id

  versioning_configuration {
    status = "Enabled"
  }
}
```

This explicitly enables:

```text
S3 Versioning = Enabled
```

---

# Step 4 — Add lifecycle configuration

Add:

```hcl
resource "aws_s3_bucket_lifecycle_configuration" "lifecycle_rule" {
  bucket = aws_s3_bucket.lifecycle_bucket.id

  rule {
    id     = "datacenter-lifecycle-rule"
    status = "Enabled"

    filter {}

    transition {
      days          = 30
      storage_class = "STANDARD_IA"
    }

    expiration {
      days = 365
    }
  }
}
```

### What this means

The lifecycle rule:

```text
Object created
     ↓
30 days
     ↓
Move to STANDARD_IA
     ↓
365 days
     ↓
Expire/delete object
```

---

# Step 5 — Configure the output

In `outputs.tf`:

```hcl
output "KKE_bucket_name" {
  value = aws_s3_bucket.lifecycle_bucket.bucket
}
```

The required output variable/name was exactly:

```text
KKE_bucket_name
```

---

# Step 6 — Initialize Terraform

```bash
terraform init
```

This initializes the working directory and downloads the required provider.

---

# Step 7 — Format

```bash
terraform fmt
```

This formats the Terraform configuration.

---

# Step 8 — Validate

```bash
terraform validate
```

Expected:

```text
Success! The configuration is valid.
```

If validation fails, don't immediately apply.

Read the error and identify whether it is:

* Syntax error
* Resource argument error
* Reference error
* Provider/resource version issue

---

# Step 9 — Review the plan

```bash
terraform plan
```

Check that Terraform intends to create:

```text
aws_s3_bucket.lifecycle_bucket
aws_s3_bucket_versioning.lifecycle_bucket_versioning
aws_s3_bucket_lifecycle_configuration.lifecycle_rule
```

Before applying, verify:

```text
Bucket = datacenter-lifecycle-7584
Versioning = Enabled
Lifecycle rule = datacenter-lifecycle-rule
Transition = STANDARD_IA after 30 days
Expiration = 365 days
```

---

# Step 10 — Apply

```bash
terraform apply
```

Confirm:

```text
yes
```

---

# Step 11 — Verify Terraform output

```bash
terraform output
```

Expected:

```text
KKE_bucket_name = "datacenter-lifecycle-7584"
```

---

# Step 12 — Verify bucket versioning using AWS CLI

```bash
aws s3api get-bucket-versioning \
  --bucket datacenter-lifecycle-7584
```

Expected:

```json
{
    "Status": "Enabled"
}
```

---

# Step 13 — Verify lifecycle policy

```bash
aws s3api get-bucket-lifecycle-configuration \
  --bucket datacenter-lifecycle-7584
```

Verify that the response contains:

```text
datacenter-lifecycle-rule
```

and:

```text
STANDARD_IA
30 days
365 days
```

---

# Step 14 — General Terraform troubleshooting flow

For future Terraform tasks:

```text
Check files
   ↓
terraform init
   ↓
terraform fmt
   ↓
terraform validate
   ↓
terraform plan
   ↓
Review planned resources
   ↓
terraform apply
   ↓
Verify outputs
   ↓
Verify actual AWS resources
```

If something fails:

```bash

terraform plan

```

For AWS resources, also verify directly using AWS CLI where appropriate.

# 4. Linux — Apache Troubleshooting on Nautilus Servers

## Task

The monitoring system reported that Apache was not running correctly on some Nautilus Application Servers.

Requirements:

```text
Servers:
stapp01
stapp02
stapp03

Apache port:
3001

DocumentRoot:
/var/www/html
```

We were explicitly instructed **not to stop or disable any firewall already running**.

---

# Step 1 — Connect to the servers

From the jump host, access each application server:

```bash
ssh stapp01
```

Then:

```bash
ssh stapp02
```

and:

```bash
ssh stapp03
```

---

# Step 2 — Check Apache status

On each server:

```bash
sudo systemctl status httpd
```

This is the first thing to check when monitoring reports that Apache is down.

Possible states include:

```text
active (running)
inactive (dead)
failed
```

---

# Step 3 — Check whether Apache is listening on port 3001

```bash
sudo ss -lntp | grep 3001
```

We needed Apache to listen on:

```text
3001
```

---

# App Server 1 — `stapp01`

## Problem found

The Apache configuration in:

```text
/etc/httpd/conf/httpd.conf
```

contained an extra semicolon:

```text
;
```

This caused the Apache configuration to be invalid.

---

## Step 4 — Edit configuration

```bash
sudo vi /etc/httpd/conf/httpd.conf
```

Removed the extra `;`.

---

## Step 5 — Start Apache

```bash
sudo systemctl start httpd
```

---

## Step 6 — Verify

```bash
sudo systemctl status httpd
```

Apache started successfully.

---

# App Server 2 — `stapp02`

## Problem found

The configuration itself was fine.

Apache was simply not running.

---

## Step 4 — Start Apache

```bash
sudo systemctl start httpd
```

---

## Step 5 — Verify

```bash
sudo systemctl status httpd
```

Apache became active.

---

# App Server 3 — `stapp03`

This server had **two configuration errors**.

---

## Problem 1 — Incorrect DocumentRoot syntax

The configuration contained:

```apache
DocumentRoot:/var/www/html
```

The correct syntax is:

```apache
DocumentRoot /var/www/html
```

The space between the directive and its value is important.

---

## Problem 2 — Incorrect Listen directive

The configuration contained:

```apache
Listen3001
```

The correct configuration is:

```apache
Listen 3001
```

Again, the space between the directive and value is required.

---

## Step 4 — Edit configuration

```bash
sudo vi /etc/httpd/conf/httpd.conf
```

Corrected:

```apache
DocumentRoot /var/www/html
```

and:

```apache
Listen 3001
```

---

# Step 5 — Validate Apache configuration

Before starting/restarting Apache after configuration changes, a good general practice is:

```bash
sudo apachectl configtest
```

Expected:

```text
Syntax OK
```

If the result is not `Syntax OK`, don't restart Apache blindly. Read the error and correct the configuration first.

---

# Step 6 — Start Apache

```bash
sudo systemctl start httpd
```

If Apache was already running and you changed configuration, use:

```bash
sudo systemctl restart httpd
```

---

# Step 7 — Verify service status

```bash
sudo systemctl status httpd
```

---

# Step 8 — Verify port

```bash
sudo ss -lntp | grep 3001
```

Expected to see Apache listening on:

```text
*:3001
```

or an equivalent listening address.

---

# Step 9 — Verify DocumentRoot

Check the configuration:

```bash
grep -n "DocumentRoot" /etc/httpd/conf/httpd.conf
```

Expected:

```text
DocumentRoot /var/www/html
```

Check the Listen directive:

```bash
grep -n "^Listen" /etc/httpd/conf/httpd.conf
```

Expected:

```text
Listen 3001
```

---

The final requirement was to verify the servers externally from the jump host.


Then:


# Today's Troubleshooting Lessons

Today's Linux task gave three different failure scenarios:

### Server 1

```text
Configuration syntax problem
        ↓
Extra ;
        ↓
Remove incorrect character
        ↓
Start httpd
```

### Server 2

```text
Configuration was fine
        ↓
httpd was stopped
        ↓

```

### Server 3

```text

        ↓

        ↓

        ↓

        ↓
Start httpd
```

This is useful because **not every service-down problem has the same root cause**. You should first inspect the service status and configuration instead of assuming the fix.
