# DevOps

## Task: Create a Multi-Container Pod with a Shared Volume

### Objective

Create a Kubernetes Pod containing two Debian containers that share an `emptyDir` volume. Verify that a file created in one container is immediately accessible from the other through the shared volume.

---

## Environment

* Platform: Kubernetes
* Pod: `volume-share-xfusion`
* Volume Type: `emptyDir`
* Shared Volume Name: `volume-share`

---

## Step 1: Create the Pod Manifest

Created a Pod manifest with two containers and one shared `emptyDir` volume.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: volume-share-xfusion

spec:
  volumes:
    - name: volume-share
      emptyDir: {}

  containers:

    - name: volume-container-xfusion-1
      image: debian:latest
      command:
        - /bin/sh
        - -c
        - sleep infinity
      volumeMounts:
        - name: volume-share
          mountPath: /tmp/ecommerce

    - name: volume-container-xfusion-2
      image: debian:latest
      command:
        - /bin/sh
        - -c
        - sleep infinity
      volumeMounts:
        - name: volume-share
          mountPath: /tmp/demo
```

---

## Step 2: Deploy the Pod

Applied the manifest.

```bash
kubectl apply -f volume-share.yaml
```

Verified the Pod status.

```bash
kubectl get pods
```

Expected output:

```text
volume-share-xfusion   Running
```

---

## Step 3: Create a Test File

Executed a shell inside the first container.

```bash
kubectl exec -it volume-share-xfusion \
-c volume-container-xfusion-1 -- sh
```

Created the test file.

```bash
echo "Welcome to xFusionCorp Industries" \
> /tmp/ecommerce/ecommerce.txt
```

Exited the container.

---

## Step 4: Verify Shared Storage

Checked the second container.

```bash
kubectl exec volume-share-xfusion \
-c volume-container-xfusion-2 \
-- cat /tmp/demo/ecommerce.txt
```

Expected output:

```text
Welcome to xFusionCorp Industries
```

---

## Verification Commands

```bash
kubectl get pods

kubectl exec volume-share-xfusion \
-c volume-container-xfusion-1 \
-- ls /tmp/ecommerce

kubectl exec volume-share-xfusion \
-c volume-container-xfusion-2 \
-- ls /tmp/demo

kubectl exec volume-share-xfusion \
-c volume-container-xfusion-2 \
-- cat /tmp/demo/ecommerce.txt
```

---

## Key Learning

* `emptyDir` volumes are created when the Pod starts.
* Every container mounting the same `emptyDir` shares the same filesystem.
* Data remains available while the Pod exists.
* Deleting the Pod permanently removes the contents of the `emptyDir`.


Displayed the resolver configuration.



* Multiple nameservers provide fallback if the primary server is unavailable.

# Terraform (AWS)

## Task: Create an AWS VPC and Subnet Using Explicit Resource Dependencies

### Objective

Provision an AWS VPC and Subnet using Terraform while explicitly defining the resource creation order with the `depends_on` argument.

---

## Files Created

```text
main.tf

variables.tf

terraform.tfvars

outputs.tf
```

---

## Step 1: Define the Provider

Configured the AWS provider.

```hcl
provider "aws" {
  region = "us-east-1"
}
```

---

## Step 2: Create the VPC

Defined the VPC resource.

```hcl
resource "aws_vpc" "datacenter_vpc" {
  cidr_block = "10.0.0.0/16"

  tags = {
    Name = var.KKE_VPC_NAME
  }
}
```

---

## Step 3: Create the Subnet

Created the subnet with an explicit dependency.

```hcl
resource "aws_subnet" "datacenter_subnet" {

  vpc_id = aws_vpc.datacenter_vpc.id

  cidr_block = "10.0.1.0/24"

  depends_on = [
    aws_vpc.datacenter_vpc
  ]

  tags = {
    Name = var.KKE_SUBNET_NAME
  }
}
```

---

## Step 4: Define Variables

Created variables.

```hcl
variable "KKE_VPC_NAME" {}

variable "KKE_SUBNET_NAME" {}
```

Provided values.

```hcl
KKE_VPC_NAME = "datacenter-vpc"

KKE_SUBNET_NAME = "datacenter-subnet"
```

---

## Step 5: Define Outputs

Created outputs.

```hcl
output "kke_vpc_name" {
  value = aws_vpc.datacenter_vpc.tags["Name"]
}

output "kke_subnet_name" {
  value = aws_subnet.datacenter_subnet.tags["Name"]
}
```

---

## Step 6: Validate and Apply

```bash
terraform fmt

terraform validate

terraform init

terraform plan

terraform apply
```

---

## Verification

```bash
terraform output
```

Expected output:

```text
kke_vpc_name = "datacenter-vpc"

kke_subnet_name = "datacenter-subnet"
```

---

## Key Learning

* Terraform usually infers dependencies through resource references.
* `depends_on` is used when an explicit resource creation order is required.
* Variables improve code reusability, while outputs expose important resource attributes after deployment.

# Overall Key Learnings

## DevOps

* Shared `emptyDir` volumes allow multiple containers within the same Pod to access the same data.
* All containers should mount the shared volume correctly for seamless data sharing.

## Linux

* DNS resolution issues can often be mitigated by configuring reliable public DNS servers.
* Always verify resolver configuration after making changes.

## MLOps

* Publishing a Docker image requires **build → tag → push**.
* Registry APIs are useful for validating published repositories and tags.

## Terraform

* `depends_on` provides explicit control over resource provisioning order.
* Organizing Terraform code into `main.tf`, `variables.tf`, `terraform.tfvars`, and `outputs.tf` improves readability and maintainability.
